# LG-11A payments design

UNAPPROVED proposal, 2026-10-15. Documents only. Recommend one local, test-only receipt contract prerequisite. No checkout, paid grant, provider selection, price, launch default, client integration or deployment is approved.

## Proposed route and authority contract

Use a small payment service with fixed server-owned catalogue revisions. The client can select a pack key, never set DB, money, currency, payment status or provider product identity. Reject supplied amount/DB overrides. Only a verified completed payment matching the server's product mapping, amount, currency, environment and merchant can create a paid receipt. A browser return page, caller-supplied receipt JSON, local ledger and local parent-gate flag establish no payment authority.

Proposed routes are POST only for sensitive operations. All response schemas are bounded and versioned.

| Route | Proposed behavior | First local prerequisite |
| --- | --- | --- |
| /api/checkout | After adult gate/confirmation, accept pack key and operation nonce; create one hosted session using server mapping and provider idempotency. Store intent before external call, reconcile uncertain outcome by same nonce. Return allowlisted checkout destination only. | Always 503 CHECKOUT_DISABLED, no network adapter |
| /api/webhook | Verify provider signature over original bytes, timestamp/replay rules and merchant/environment. Reduce known paid/refund events into one receipt transaction; acknowledge only after durable commit. | Reject all HTTP events; inject explicitly mock verified events only through tests |
| /api/redeem | Authenticate purchaser capability, authorize receipt, return stable canonical signed receipt and current status. Repeat retrieval has no DB-side credit or global consumed flag. | Test-only invocation with synthetic capabilities and mock-only receipt domain |
| /api/recover | Authenticate parent-held recovery code in request body, return bounded paginated purchase history and receipt retrieval authority. No email lookup or unauthenticated receipt enumeration. | Test-only synthetic history, no public recovery form |

A return URL may indicate only that checkout finished navigation. It carries no recovery code or bearer receipt authority. The later client obtains status using its private checkout capability, or the adult enters their recovery code behind the parent gate. Pending/unpaid/cancelled returns grant nothing. Paid webhook after a lost redirect remains recoverable. If a checkout call times out, reuse/reconcile its operation nonce rather than creating another order.

## Minimal data and atomicity

Propose receipt rows with internal opaque receipt ID, unique provider payment ID, provider/environment, catalogue revision, pack key, fixed DB grant, settled money/currency, paid time, status and monotonic status revision. Keep a bounded event deduplication record keyed by provider/environment/event ID and a checkout-intent record keyed by operation nonce with immutable pack selection. Recovery records link a code verifier to authorized receipt IDs. A code is a bearer secret, not a player identifier. No player name, email, age, save, earned balance, device fingerprint or free text belongs in these records.

Correct the draft {id,email,pack,db} pseudocode by omitting email. Provider-held adult payer details stay at the provider. Parse only required webhook fields and never persist full payloads. A future provider may require adult recovery-code delivery through its receipt channel; that capability must be verified before selection. Do not assume it exists. Alternative adult-only code display/export after authenticated checkout requires an owner decision and proof that response loss still permits recovery. Losing every capability is an unresolved support case, not a promised email recovery service.

Use a transactional store for the future authoritative receipt state. Unique event insertion, unique payment receipt creation and allowed status transition must commit together. Duplicate event IDs return the recorded result; distinct events for the same payment cannot create another receipt. Conflicting immutable amounts or products are quarantined for review, never overwritten or converted to caller DB. Out-of-order paid/refund events require provider-specific ordering or authoritative reconciliation; a late paid event must not silently undo a refund.

D1 is the recommended later Cloudflare implementation because these linked uniqueness and rollback requirements need atomic statements. Cloudflare documents transactional batch rollback on statement failure. KV documents concurrent same-key overwrites, so a read-then-write redeemed flag in KV is unsuitable. This is a design inference from [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/) and [KV writes](https://developers.cloudflare.com/kv/api/write-key-value-pairs/), checked 2026-10-15. A conditional update affecting zero rows is not automatically a SQL failure; schema constraints and result handling must prove each transition. Do not add KV, queues or Durable Objects without a concrete unmet need. The first mock models atomic commit/failure; it does not prove D1 concurrency.

A database commit and a provider API call cannot share one local transaction. Persist checkout intent, use provider idempotency, and reconcile uncertain results. A signing failure after a committed paid receipt leaves it retrievable; it must not cause another receipt/grant. Signed envelope fields include version, domain/environment, receipt ID, catalogue revision, pack, DB, paid time, status revision and key ID. Use a reviewed asymmetric signature scheme later; private keys stay server-side, only public verification keys reach the client. Mock keys/domain never authorize production.

## Retrieval, application and restoration

Replace globally redeem once with globally issue one stable receipt per verified payment, retrieve repeatedly by authorized purchaser, and apply once per retained local ledger. Marking a receipt consumed before the client save acknowledges would lose purchases after response loss. Marking it consumed afterward cannot atomically cover a remote localStorage write either.

A later separately leased client verifier checks authentic origin, signature, domain, version, key ID, allowed pack mapping, safe integer bounds and exact receipt identity before handing a typed grant to the actual save owner. It rejects unknown/mismatched receipts without deleting saved purchases. In one acknowledged candidate, add a namespaced credit such as paid:<environment>:<receiptId> and increase bought/boughtTotal by the fixed amount. Same ID and exact same payload returns already applied; same ID with different content holds for review. Persist receipt proof and credit together. Do not publish success or live DB before acknowledgement. A lost response permits retrieval of the same receipt; a failed save retries the same grant; a successful save followed by lost UI acknowledgement finds the durable credit and adds nothing. Existing reward/away obligations settle first through their actual owner. No caller-provided DB, direct rewardCommit network call or replacement save snapshot.

This application protocol is a proposal, not an existing export. It requires a new versioned paid-source validator, pending/Retry integration, cold recognition and admission/all-writer work. Master LG-11 owns worker/** and no Ops edits. A later client lease must explicitly name the minimal new client module plus exact Rewards/Ops/Economy/gate/shell/SW sites needed after a read-only seam review. Do not widen the existing settlement kind or manufacture a successful guard. Public activation waits for that separately approved client protocol and unresolved LG-02 admission/effects prerequisites.

Recovery history answers what money bought and when, including refund status. It cannot reconstruct how much DB was spent, earned claims, local catalogue ownership, Undo state, room progress or a lost save. Replaying all paid credits into an empty ledger can restore original purchased DB, but can also recreate previously spent DB. Keeping an existing ledger avoids that duplicate through stable IDs; a new device has no such history. The server cannot infer spend from provider purchase records.

Recommended owner choice for later accountless use is explicit restoration of original purchased credits into a designated replacement save, with accepted local-copy/duplicate-spend limitations. This is UNAPPROVED and must not be advertised as balance sync. An alternative exact spent-balance/entitlement restore needs a durable spend/entitlement ledger and authenticated ownership model, which is a larger separate design. Q5 permanent catalogue items alone does not solve currency spending history. Q6 no accounts does not grant cross-device consistency. No silent summing of two saves or overwrite of earned balance. Parent code authorization permits retrieval, not proof of exclusive device ownership.

Local save editing remains an accepted single-player trust limit. Server verification protects paid issuance and recovery, not every local action. Never add anti-cheat that deletes legitimate purchases, removes their history or silently revokes local items on a network failure.

## Failure, secrets and family boundaries

The game continues earned DB display/spending when the backend is unavailable or the store is hidden, once the separate free Vault implementation is ready. Backend failure must not block ordinary play. Unknown payment status stays pending; retry offers status retrieval rather than another charge. Local save holds use the existing exact Retry owner and disclose acknowledgement limits; server availability is not a reason to erase a local receipt.

Before live use, decide refunds/chargebacks, partial refunds, already-spent bought DB, entitlements purchased using mixed sources, supporter eligibility and restore eligibility after refund. Recommend retain immutable payment/history and append status revisions, stop new restoration of refunded grants, and preserve local progress/items pending an approved policy. No automatic negative balance, earned-DB clawback, item deletion or cash-refund promise. Offline clients cannot learn immediate revocation. A signed older receipt cannot by itself prove current refund status; online status revalidation before a new restore and an owner-approved offline policy are required. Local Undo remains distinct.

Proposed bounds for a future implementation: 4 KiB checkout/redeem/recover bodies; bounded webhook size selected against the chosen provider; 100 history rows per page; code attempts initially 5/minute per short-lived network bucket and code verifier, with generic errors and Retry-After. These are UNAPPROVED test parameters, not provider/platform limits. Verify legitimate household retries and webhook retry behavior before release. Avoid permanent lockout of a valid purchaser. No durable raw IP log; any transient limiter metadata and retention require privacy review.

Generate high-entropy recovery capabilities, retain only keyed verifiers, compare safely and rotate through an authenticated recovery path if later approved. Never put codes in URLs, analytics, referrers, error messages, console output or access/request-body logs. Use no-store on sensitive responses, HTTPS for live traffic, strict origin/CORS rules for browser routes and provider-only webhook authentication. Gate public checkout separately from same-origin request checks. Bound parser work and reject unsupported methods/content types before processing. Logs contain only opaque correlation ID, event type and result code with a proposed short retention period selected before live use. Secrets, webhook keys and signing keys use future environment secret bindings, never repo/client fixtures. No credentials or real payer records are needed for the mock.

Parent gate, quiet store, hide-store and ad-free/kids rules are fixed. Treat every player as a possible minor. No name/email/age fields, identifying analytics, chat, ads, gacha, FOMO or sold progression/automation. Before specifically navigating to provider-hosted adult checkout, require the parent challenge and explicit cost confirmation; cancellation stays in game. Allowlist the provider destination, use a bounded return destination and avoid arbitrary external links. Ordinary play stays contained. Hide-store removes prices/packs/buy controls while preserving balances, ownership and recovery of already-owned purchases. Existing LG-02 earned-only hide-store wording differs from later paid-store scope; reconcile presentation under the later client lease. No final gate or legal copy is authored here. A parent gate is product behavior, not a legal-compliance guarantee. LG-12 and owner's qualified legal review remain prerequisites before first sale.
