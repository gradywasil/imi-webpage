# LG-01 independent design review r1

**Verdict: REQUIRES DOCUMENT REPAIR.** The proposal is suitable for owner discussion of the explicitly marked amounts and policies after three reliability/seam statements are repaired. This is a documents-only review, not implementation acceptance. Owner approval and a separate implementation lease remain required.

## Material findings

1. **FAIL — claim recovery has no defined behavior when the prepare write fails.** [Design, “Normal eligibility” and “For letters, DB and tokens” (lines 65–67)](LG-01-reward-design.md#claim-identifiers-and-state-lifecycle) say to persist the locked descriptor before delivery, but also say to retain it for retry if storage fails. In the actual Ops source, `save()` catches and suppresses a failed `localStorage.setItem` ([ops.js:205](../../../ops.js)); therefore a failed prepare write leaves no durable descriptor. A reload can lose the locked letter/cash amount, its sampled desk/rate/origin, or the fact that a first clear was prepared. For an award, the source sets the award boolean before emitting the extension event ([ops.js:1264–1276]); an ordinary save can fail too. This is a design-contract gap, separate from the later failure-injection proof.

   **Repair needed:** state the commit boundary and storage-unavailable guarantee. At minimum, never report saved or deliver until preparation is durably acknowledged; say what happens if that acknowledgement fails and how a later load distinguishes a durable unclaimed milestone from a lost event without resampling a different reward. If that cannot be guaranteed with the accepted save lifecycle, explicitly narrow the guarantee and obtain owner approval before implementation. Apply the same rule to Ops-only rewards and the cash cross-key protocol.

2. **FAIL — the single-writer requirement is not an implementation contract yet.** [Design, last paragraph of “Claim identifiers and state lifecycle” (line 73)](LG-01-reward-design.md#claim-identifiers-and-state-lifecycle) correctly rejects localStorage as compare-and-swap, but only asks for a guard “or equivalent lock.” The two tabs can each load the same Ops/wallet markers and prepare or credit the same logical claim. The design needs a minimum feasible policy and its failure behavior, or an explicit lease prerequisite that names the chosen mechanism and guarantees recovery/release on tab close/crash. This can remain a small local-save guard; no broader account or anti-cheat framework is needed.

   **Repair needed:** specify whether the game is single-writer by refusing a second active tab, or provide another concrete serialization policy. Define lock acquisition before rewards/offline work, behavior when unavailable, and stale-lock recovery. Keep verification of the chosen policy in later acceptance.

3. **FAIL — persisted rush expiry cannot be applied to the current away interval through the described hooks.** [Design, “Stored golden reward” (line 85)](LG-01-reward-design.md#stored-golden-reward) requires splitting an offline interval at reward expiry before paying royalties/divisions. Current Ops calls `simulateAway`, pays the accumulated royalties/divisions, then emits `away` ([ops.js:1423–1507]); the accepted `away` extension event is therefore too late to split that interval. The receipt acknowledges this, but the design’s required future seam is not stated in the reward contract. Without a pre/during-away boundary, expiry can be applied to the entire absence or none of it, contrary to the promised exact 15 game seconds.

   **Repair needed:** explicitly make a narrowly scoped pre/during-away simulation seam part of the future implementation lease, with reward-timer expiry and production payout split at the boundary, and mark exact offline rush behavior unverified until that seam exists and is accepted. No change to the deferred away endpoint policy is implied.
