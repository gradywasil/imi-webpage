## New material findings

### R2-01: Checkpoint deletion can discard the uncovered pre-hold tail

Priority: high. Candidate lines 107 and 135 conflict for an existing checkpoint whose endpoint precedes the new transition boundary. Line 107 requires finishing that checkpoint and then settling its uncovered tail. Line 135 requires checkpoint deletion to acknowledge `lastSeen=resumeWallMs`, and says any fresh-load tail starts there. The proposed descriptor contains `boundaryEndWallMs`, `resumeWallMs`, `oldEffects` and `phase`, but no explicit remaining-tail start after the old checkpoint is deleted.

Concrete paper sequence, seconds on one wall-clock axis:

1. An interrupted checkpoint ends at 100. A fresh transition/recovery at 106 still owes that checkpoint plus ordinary old-effect work over [100,106]. The checkpoint alone owns its original cursor/report/sold references.
2. Recovery holds from 106 to 126. Acknowledged compensation saves the old checkpoint and descriptor `{boundaryEndWallMs:106,resumeWallMs:126,...}`. Only [106,126] is excluded productive time.
3. The old checkpoint finishes. Following line 135 literally deletes it and writes `lastSeen=126`. Reload occurs immediately after this acknowledgement, before a replacement tail checkpoint is prepared.
4. The saved checkpoint endpoint 100 is gone. Starting the fresh tail at 126, as instructed, skips the six seconds [100,106]. Keeping the descriptor does not recover its missing start; `phase` has no specified durable interval payload. Deleting it at the same point is worse. Reusing the now-advanced `lastSeen` cannot recover those six seconds either.

The source makes this a real integration boundary: `ops.js:1626-1631` acknowledges completion separately from deletion and advances `lastSeen`; `ops.js:1836-1844` preserves checkpoint/report/sold identity during reward publication. `rewards.js:455-484` retains fixed payment identity/next phase before fallible preparation. A new design must preserve these obligations across each acknowledged key, not only while a volatile Vault intent still knows the old endpoint.

Smallest correction: specify the durable handoff from old checkpoint completion to the owed tail before advancing beyond it. For example, atomically replace the completed checkpoint with the next bounded old-effect checkpoint, or retain a validated pending-tail start/end until that tail is acknowledged. Advance to the hold-exclusion resume boundary only after all work preceding the hold is covered. Keep one simulator and one cursor; do not add a second income journal. Define repeated holds and the later [resume,activation] segment so they neither disappear nor become hold time. Add reload exactly after old-checkpoint deletion and before tail preparation, including two holds with productive time between them. This correction belongs to the named Ops/Rewards boundary and descriptor lease.

### R2-02: Compensated challenge timestamps use the wrong basis for an old fixed-end tail

Priority: high. Candidate lines 121, 131 and 135 require adding signed hold wall elapsed to saved `challenge.start`, acknowledging that compensation before productive continuation, preserving an existing checkpoint's original `deadline`, and using the captured fixed endpoint for a new checkpoint's initial Deadline calculation. Those instructions are consistent for continuing the already-computed checkpoint. They are not sufficient for creating an uncovered historical tail after it finishes.

`ops.js:1502` calculates the new timed checkpoint deadline as `(duration - (end - awaySec*1000 - challenge.start)/1000)/G`; lines 1514-1525 preserve its early/advance stages, and lines 1573-1597 use the resulting sale/expiry boundaries. `advanceDeadlines` at 379-385 also shifts the saved challenge start for game acceleration. The repaired fixed endpoint corrects the old use of a later Retry's Date.now, but it must share a clock basis with the challenge timestamp.

Paper example: after settling the old checkpoint through wall time 100, the challenge has one game second remaining, with old G=2. The unpaid old tail is [100,106]. A 20-second hold has already added 20 to saved challenge.start before that tail is created. Computing the tail at the original endpoint 106 with the shifted start gives `(1+20)/2 = 10.5` real seconds until expiry, instead of `1/2 = 0.5`. A qualifying sale after 0.5 seconds can now clear a challenge that should have expired. This is independent of R2-01: merely preserving and replaying the lost tail would expose this clock error. An existing checkpoint's preserved deadline does not supply the next checkpoint's missing clock transform.

Smallest correction: define the effective saved-timestamp view for every pre-compensation interval. The historical interval must use the unshifted challenge basis, or explicitly reverse only compensation belonging after that interval when calculating its deadline. Preserve actual wall endpoints for world/weather sampling. Do not shift the whole simulator into fictitious wall time. Carry the necessary bounded compensation provenance through acknowledged recovery, or order compensation after all historical work with a separately specified safe durable hold exclusion. Include crop readiness, visible-phase challenge checks, positive/negative wall jumps and repeated holds in that same temporal contract. Do not recalculate an existing checkpoint's locked deadline or paidSeconds. Add the one-second/G2/twenty-second example at reloads before and after compensation and tail preparation.

### R2-03: One unlocked absence read cannot establish the proposed shared-save protection

Priority: medium for the prospective shared-save gate; shared-save enablement must remain blocked. Candidate line 151 reads `imi-ops-v1` once before Rewards/Core/Economy and sends a conclusively absent Vault save down the exact original unlocked path. Lines 153 and 219 then promise blocking before all loaders/writers/reset for Vault-bearing saves, but their narrow guards are described for recognized/blocked state. Only the both-flags path expressly rereads under ownership.

Counterexample: a current fully unflagged document A reads no `prem.vault`; it pauses between external script loads. A current opted-in document B acknowledges the first Vault purchase. A continues into Core/Economy on its cached no-Vault classification. This requires no stale SW or old source. `economy.js:31-32,75-101` currently permits disabled writes and drops reward wallet metadata in the ordinary save shape; Core loads at 94 and registers direct lifecycle writers at 99-101; Ops' disabled reset at 2967 clears namespaces. The both-flags reread never runs in A. The same exposure exists for a no-Vault document admitted before a later purchase, unless the supported-use restriction explicitly excludes that transition.

The design correctly says old noncooperating writers cannot be controlled and requires closing old game documents. It also correctly retains isolated task-origin/save-only purchase exercises until a gate passes. Those are useful restrictions. They are not evidence that the one-time classifier controls a current cold document crossing from no-Vault to Vault-bearing between recognition and loading, or a previously admitted current disabled writer. The later matrix's changed-keys-before-acquisition case covers only a path that actually acquires.

Smallest correction: retain the isolated single-document purchase boundary as the only supported purchase mode until this is resolved. Explicitly document the same-build first-purchase/admitted-writer race and the limits of any recognition result. If shared-save protection is still proposed, specify how subsequent loaders/writers revalidate a current classification under a cooperating ownership protocol, and reconcile that change with the exact unlocked no-Vault path. A fresh unlocked read at each write alone is not atomic exclusion. Do not silently widen all default paths to use locks or claim this is an accepted LG-01 defect. An expressly narrowed supported-use contract is an alternative to extra machinery. Test current/current races separately from stable cold bookmarks and stale-source incompatibility. No general scheduler/bootstrap rewrite is justified.
