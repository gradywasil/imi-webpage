# LG-10A expanded awards design

UNAPPROVED PROPOSAL, 2026-10-15. Documents only on dirty shared `long-game`. No new award, amount, pool, historical grant, income perk or implementation is authorized. Existing source and prior decisions remain unchanged.

## Recommendation

Build ten recognisable long-game awards first, making 78 in the contained opt-in build. Reuse the existing automatic reward claim engine, award cards and three-goal selection. Keep the 68-row base catalogue byte-for-byte in place. Put new definitions in one small `awards-catalogue.js` module, with ten explicit rows rather than a general catalogue generator. The roughly250 target is a planning envelope, not this build's content obligation.

These awards recognise combinations or progress beyond existing first clears. They do not reissue layer firsts, challenge firsts, helper unlocks, Playbills or Works speed bonuses. No new progression gate follows from earning them. Six Letters rewards, two fixed Royalty Rush tokens and two DB rewards are proposed. There is no cash reward in this slice, reducing wallet coordination changes. Each new award adds one percentage point of permanent award income, subject to separate owner approval below.

## Exact reward quantities and permanent effect

L means the existing Silver balanced-Letters descriptor for all six L rows. Let Lrate be `rewardBasis().letters[basis.desk]` for the highest owned desk, including speed once and excluding temporary typing buffs. Quantity is `floor(max(50,min(20000,300*Lrate)))`, locked with desk, rate, minutes5, floor50, cap20000 and speed at discovery. Split across26 uppercase letters with remainder A through Z. At Lrate2 this gives600; at zero it gives50. Delivery adds inventory only, never typed/harvest/manual-proof counters. Six L rows total300 minimum to120000 maximum letters if all are live, each sampled separately. Reusing the formula is proposed assignment authority, not approval of the new rewards.

G means exactly one stored Royalty Rush token per G row, two total. Existing effect is x7 royalties/division income for15 game seconds, no random draw, no DB, no caught-gold counter. Stored and consumed tokens both retain the original logical award source. Native/reward rushes do not multiply to x49; current expiry and reset semantics remain. One source recogniser must serve validation, reconciliation, inventory, activation and Retry. A consumed token is proof of prior delivery and must never trigger replacement.

D is2 DB for `lg10-imprint-quartet` and4 DB for `lg10-estate-two`,6 maximum. Logical reward IDs add the `award:` prefix to each table ID; changing catalogue version or copy never changes these IDs. No reward itself adds stamps, completes series, clears challenges, sets manual proof, increments Estate count, restores deposits or advances Works tokens. Letters can feed later ordinary production but delivery cannot recursively evaluate awards. The normal finite sweep handles later progression once per ID.

All68 original awards yield1.68 award multiplier when earned. All ten new ones take it to1.78, +10 percentage points on the base income multiplier and `1.78/1.68-1 = 5.95238095%` relative income at full original completion. At n existing earned awards, relative uplift after k new is `0.01*k/(1+0.01*n)`. It is not ten successive multiplicative1.01 boosts. If250 total awards all inherited this perk, factor3.50 versus1.68 is108.33333333% more; this proposal does not approve that eventual multiplier. New Works awards do not add typist-rate points or raise the accepted Works1.07 cap.

## Historical policy requiring a separate decision

Recommend new explicit policy `lg10a-db-only-v1`, UNAPPROVED. Under the actual writer lock, after existing recovery settles and before any expanded discovery, snapshot exactly which of these ten predicates the acknowledged source save proves. Persist that finite ID list and policy version once, even if empty. Do not reuse or alter LG-01's migration list. Historical qualifying rows receive their award bit/+1% and a quiet receipt; the two D rows may Claim their2/4 DB automatically once, L/G rows receive an explicit waiver and no inventory. This new policy must specifically approve the possible6 historical DB and +10 income points. LG-01's historical policy supplies no authority for it.

Every row can qualify historically only from the table's validated current saved proof. Folio completion must be current; reset-lost completion cannot be recovered from gallery. Existing explicit challenge done bits and finished manual proof are adequate local saved facts, not reconstructed ownership from aggregate statistics. Archive uses two active fully deposited entries, with no fabricated clock history. Works uses validated first-play progress, not total letters. Missing proof remains unfinished and can earn the live reward later. Already-recorded expanded awards/claims override snapshot processing. Never substitute `silent`, save age, missing receipt or a higher unrelated counter for policy membership.

After the snapshot, discoveries receive normal live one-time rewards, even if their underlying proof originated earlier but was absent from that snapshot. Persist bit and fixed descriptor together before delivery; a failed initial save grants nothing and exact Retry retains the candidate while alive. Durable prepared records settle through existing recovery; committed/waived records never repay. New policy exceptions must be limited to these exact IDs and versions, leaving original waiver validation and all legacy receipts intact. No backfill menu, general migration framework or rerunnable correction campaign is proposed.

## Smallest later module and lease

Recommend `awards-catalogue.js`, a plain script loaded after its proof owners and before Ops registration, with frozen ten-row definitions, read-only validated predicates, goal metadata and the exact new policy. `window.__OPS_EXTENSIONS` registers one namespace. Ops remains owner of actual state transitions and award presentation. Keep existing AWARDS literal and append only enabled new descriptors to a private combined view used by check/render/reward/goal APIs. Do not expose mutable global AWARDS or add general mutation APIs. Existing original source order stays first; new rows follow table order.

Proposed optional state is `S.meta.expandedAwards = {version:1,policy:'lg10a-db-only-v1',historicalIds:[...]}`. S.awards stores the ten permanent award bits, Rewards claims store standard receipts, prem.credits stores only the two D sources, and storedGold stores the two G sources. No duplicate earned counter or milestone event log. Receipt proof should retain the bounded qualifying source subset and rule1 at unlock so subsequent resets cannot reinterpret a grant; keep content identity/index for Works and explicit source records for composites. A module pure candidate builder can stage metadata/bit/descriptor, with the existing reward owner acknowledging before publication. No per-frame scans beyond ten bounded rows and no background writer.

Rewards needs a tiny fixed lookup for new rows in row/eligible, narrow new historical-policy handling, and shared gold source recognition covering stored/consumed records. Keep original assignments literal unchanged. Cold validation must recognise these exact sources even before feature registration. Absent/default-off saves create no new state or effective hooks. A save containing expanded metadata/award IDs/claims/credits/tokens without the new opt-in must stop at the early gate with Resume/Retry, before legacy writers can count new bits while ignoring reward sources. Unknown version, orphaned delivery, contradictory policy or unsupported proof holds and preserves raw bytes. Do not silently delete/waive/recredit malformed new records.

New awards must be retained through ordinary Printing, Imprint and Estate exactly with S.awards/rewards/meta; source evidence for a previously earned card need not remain currently eligible. Run-scoped unfinished Folio/shelf goals may lose progress after reset. Do not rewrite reset projections; source currently retains these containers. Full local reset follows existing current timeline policy, without deciding permanent paid restoration. Any required Core/full-reset preservation change is a genuine unowned prerequisite, at Core reset handling and Ops reset hooks, requiring its own minimum named lease before implementation. This design has found no need for that change and grants no Core/Economy authority.

The concrete missing prerequisite is catalogue/source integration, currently private `rewards.js` row/eligible/normalize/historical/goldSource and `ops.js` AWARDS consumers. Minimum later lease must explicitly include those functions plus `vault-save-gate.js` pre-boot recognition. A module-only lease cannot safely ship new DB/G claims. The automation extension already exports validConfig and validMuse at automation.js:593; Ops already exports validPitch/validMedia. A narrow read-only facts adapter in Ops can use those existing exports with the candidate state and owner context. No new automation.js export is currently justified.
